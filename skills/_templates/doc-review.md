# 文档审查（两把尺子）

> 本文件是**协议与清单**，不是任务产物模板。小审（S1–S4）与大审（D1–D7）的维度、证据规则与不采用项只在
> 这里定义；其他技能交叉引用本文件，不要在别处复制第二份。
>
> 引用者：`dsh-trellis-sun-feat`（review 阶段跑小审）、`dsh-trellis-sun-check`（复核小审结论）、
> `dsh-trellis-sun-issue` / `dsh-trellis-sun-refactor`（按需）、`dsh-trellis-sun-doc-review`（跑大审）。
> **审查者只写自己的报告或阶段产物的一节，不修改被审文档正文。**

## 分级

| 级别 | 何时 | 范围 | 维度 | 产物 |
|---|---|---|---|---|
| 小审 | 随任务：feat `review` 阶段，与 code review 同轮 | 本任务 2–4 份产物 | S1–S4 | 现有阶段产物的一节（`review.md` / `fix-note.md` / `apply-notes.md`） |
| 大审 | 版本冻结 / 文档定稿 | 由配置与文件树算出 | D1–D7 | `.trellis/reviews/<yyyy-mm-dd>-doc-review.md`，`status: draft` |

- 纪律：**小审不攒问题等大审；大审不重扫小审已逐条过完的内容**，只做跨文档与深度维度。
- **大审不卡任何门禁**；只有小审的 S1 / S2 / S3 命中且未处理，才禁止宣称 review passed。

## 证据规则（两级共用）

每条意见必须给三样，缺一不成立；**没有引用的意见直接删掉，不算发现**：

1. **位置**：`文件:行号`（Markdown）或章节锚点（无行号时，如章节标题）；
2. **引用原文**：逐字复制，不改写、不概括；
3. **依据**：可核对的证据（命令与输出 / 文内另一处原文 / 目标是否存在），或显式写
   「需外部核对：<要核对什么>」——**核不了的不许下结论**。

反例：把「这里写得不太清楚」当发现；把猜测写成结论；引用与原文对不上。

## 小审：S1–S4（随任务，轻）

| id | 查什么 | 怎么查 | 命中级别 |
|---|---|---|---|
| **S1** 引用能落地 | 文中出现的路径、文件名、工具名、命令、版本号、章节引用：目标还在，名字对得上 | `glob` 定路径、`grep` 定名字、命令跑 `--version`；逐个核 | P1 |
| **S2** 没有占位与空洞 | `TODO`、`待补`、`<...>`、`（略）`、只有标题没有正文的章节、声明了却空的表格 | 检索占位词 + 逐节看标题后的第一段 | P1 |
| **S3** 验收可测 | 每条验收标准都写得出验证入口（命令 / 质量门 / 人工确认），且能被判成通过或不通过 | 逐条问一句「怎么判定通过？」；答不出即命中 | P1 |
| **S4** 文内自洽 | 同一数字、版本、名字、编号在被审文件集内部多处出现时一致 | 交叉比对（只比被审集合内部，不做跨文档对账） | P2 |

- 结论三态：`通过` / `有问题`（逐条列）/ `无法判定`（写明缺什么）。
- 维度表必须**逐文件**填；行数与被审文件数对不上即视为未完成。
- 语言润色与文档定位（Diátaxis）**不在**小审范围——那是大审的事。

### 小审结论的落法

写进阶段产物的一节（feat → `review.md`；issue → `fix-note.md`；refactor → `apply-notes.md`）：

```markdown
## 文档审查（小审）

| 文档 | S1 | S2 | S3 | S4 | 结论 |
|------|----|----|----|----|------|
| `prd.md` | 通过 | 通过 | 有问题 | 通过 | 需修 |

| 编号 | 维度 | 级别 | 问题 | 位置 | 引用原文 | 处理 |
|------|------|------|------|------|----------|------|
| DR1 | S3 | P1 | AC-3 判不出通过与否 | `prd.md:42` | 「体验要顺滑」 | open |
```

## 大审：D1–D7（版本冻结，重）

| id | 维度 | 查什么 | 怎么查 | 默认级别 |
|---|---|---|---|---|
| **D1** 真实性 | 每个事实性断言（版本、命令、路径、工具名、签名、计数、外部标准）站不站得住 | 能核的核到输出；核不了标「需外部核对」；禁止编造 | P1（核到即错）／核不了则不判级 |
| **D2** 完整性 | 声明要有的章节都在且非空；承诺的每项都有落点 | 逐节清点，对照目录与正文 | P1（缺了声明的必需件） |
| **D3** 跨文档一致性 | 同一事实在多份文档里的表述一致；跨文档引用能解析 | 建「同一事实 → 各文档表述」对照表 | P2 |
| **D4** 结构逻辑 | 章节顺序与层级服务文档用途；结论依赖的前提先出现；不拿结论当依据 | 顺着读，画出论证依赖 | P2 |
| **D5** 可验证性 | 验收标准可判定，且写明验证入口 | 同 S3，但覆盖全部文档与全部标准 | P1 |
| **D6** 语言质量 | 语法、术语、大小写、中英混排、歧义长句 | 按 P1 改义 / P2 影响执行 / P3 润色分级 | P3（改义或损可信度升 P1） |
| **D7** 文档定位 | tutorial / how-to / reference / explanation 定位单一、不串味；受众匹配 | Diátaxis 四象限分类，标出混装段落 | P3 |

「默认级别」是起点不是结论：最终级别按影响面判定，**P1 必须先过自证伪**（见下）。

**判定权分离**：事实、语言、结构分三张表出结论，互不越界——查事实的不做校对，做校对的不判对错，
谈结构的不改技术细节；合并时保留各自的位置引用。

### 大审报告骨架（8 节）

```markdown
# 文档审查报告 — <范围>

status: draft      # draft | confirmed（人 或 dsh-trellis-sun-check 复核后才转 confirmed）
snapshot: <git rev-parse HEAD>
round: 1

## 1. 文档清单与定位
| 文档 | 定位（Diátaxis） | 受众 | 行数 |

## 2. 覆盖图
| 文档 | 章节 | 状态（读到 / 跳过 / 无法读） | 原因 |
覆盖百分比：<n>%

## 3. 七维发现（D1..D7 各一张表）
| 编号 | 级别 | 问题 | 位置 | 引用原文 | 依据 | 自证伪结论 |

## 4. 跨文档一致性对照
| 同一事实 | 文档 A 的表述 | 文档 B 的表述 | 判定 |

## 5. 需外部核对清单
| 断言 | 位置 | 要核对什么 | 谁能核 |

## 6. 优先级与整改建议
| 级别 | 条目 | 改法 | 工作量 |

## 7. 限制与未覆盖
## 8. 运行信息（快照、审查者、轮次、范围推导过程）
```

### 大审的执行纪律

- 范围只能由 `.trellis/doc.json` 的 `files`（无配置时 `$root` 目录树）加 README / CHANGELOG 与本版本任务产物
  **算出**，推导过程写进 §8；不许凭印象列文件。
- **自证伪**：准备判 P1 的发现，先写「什么证据能推翻它」并试着推翻；推不翻才升 P1。
- 报告落 `.trellis/reviews/<yyyy-mm-dd>-doc-review.md`；`draft` 不许当结论，转 `confirmed` 才算。
- 不改被审文档一个字；结论只进版本记录（journal 记一笔：跑了 / 结论 / 未覆盖）。

## 与 check 的分工

| | 核什么 | 什么时候 |
|---|---|---|
| `dsh-trellis-sun-check` 矩阵第 5 行 | 实现是否**满足**验收标准 | 写码之后 |
| 小审 S3 | 验收标准**本身**可不可测 | 写完 prd 即可见 |

两者不互相替代：标准本身不可测时，check 的「逐条核对」只是把一条不可测的标准再核一遍。

## 明确不采用

- **PDF / DOCX / OCR 管线**：本插件没有 `doc_read` / `pdf_read` / `doc_ocr`，只审仓库内 Markdown。
- **多厂商评审团**：owner 2026-11-27 明确不看好，不往这个方向做。
- **批注 UI**（人审类插件）。
- **机械一致性对账**（版本号 / 更新记录 / 结构树 / 计数与代码及文档间对账，doc-guard 方向）与
  **口径钉扎**（canon-keeper 方向）：未定，另行处理，本轮不做。
