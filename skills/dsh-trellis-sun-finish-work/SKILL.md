# dsh-trellis-sun-finish-work

当任务实施与验证完毕、准备标记完成或归档时运行本技能。

## 第 0 步：应用 spec-delta（feat 轨道，归档前；没有该文件不阻塞）

顺序是 **update-spec（教训）→ 应用 spec-delta → 业务提交**。delta 是事前批准的契约增量，归档时逐条机械合并：

1. **先看文件在不在**：任务目录里**没有 `spec-delta.md` → 视为无增量，直接继续收尾**，不要停下询问。
   属于这一类的情形：1.1.0 之前创建的老任务（模板尚未播种）、issue / refactor 轨道、以及明确省略的 quick 改动。
   也不许凭记忆或凭 prd 临时补写一份 delta——没写就是没写，只在日志记「无 spec-delta（<原因>）」。
2. 文件存在则读 `status`；不是 `approved` → **停下询问用户**，禁止合并。
3. 逐条应用 `ADDED` / `MODIFIED` / `REMOVED`；目标文件只能是 `.trellis/doc.json` 的 `files` 或 `$root` 下的常驻文档。
4. 逐条核对，任一不满足即**停下询问**，禁止静默合并：
   - `MODIFIED` / `REMOVED` 的旧文本与目标文件**当前内容逐字一致**（含空白与标点）；
   - `ADDED` 的章节锚点存在且不重复；
   - 目标文件存在，且不在任务目录内。
5. **只做机械替换**：不顺手改写、不「优化」措辞、不合并相邻条目。
6. 每条结果写回 `spec-delta.md` 的「合并记录」（applied / skipped / failed + 说明），并在 `.trellis/journal/<yyyy-mm>.md` 记一笔。
7. 合并产生的 spec 改动与业务代码**同批提交**（下面第 1 步），不单独开提交。
8. 若某条 lesson（update-spec 写入）恰好落在 delta 瞄准的同一章节导致核对失败 → **停下询问**：这是预期行为，不是 bug。

## 收尾标准提交流（三步走）

提交顺序必须为：**业务实现提交（Work commit） $\to$ 任务归档提交（Archive commit） $\to$ 研发日志提交（Journal commit）**。绝不要将工作流簿记与实际业务改动混在一起。

| 步骤 | 操作目标 | 具体动作 / 工具 | 重点要求与注意事项 |
|---|---|---|---|
| 1. 提交业务代码 | 提交业务实现 | `git commit` 提交业务实现与测试文件 | 先提交业务代码；**除非用户明确要求，否则绝不擅自执行 `git push`** |
| 2. 标记任务完成 | 标记完成 | 调 `sun_trellis_task_update({ status: 'completed' })` | 工具会执行严格的 Git 干净度硬门禁检查 |
| 3. 安全归档任务 | 归档持久化 | **征得用户同意后**，调 `sun_trellis_task_archive({ slug: '...' })` | 自动移动到 `.trellis/tasks/archive/<yyyy-mm>/<slug>/` 并解绑会话指针 |
| 4. 沉淀研发日志 | 追加月报 | 在 `.trellis/journal/<yyyy-mm>.md` 追加本次交付摘要 | 更新任务索引，记录本次交付的业务价值与关键改动点 |
| 5. 完结汇报 | 告知用户 | 向用户明确指出归档记录与代码提交的落脚点 | 告知任务已成功收口 |

## 作用域放宽机制（Scoped relaxation）

`sun_trellis_task_update(status: 'completed')` 与 `sun_trellis_task_archive` 内置了严格的 Git 干净度门禁。
- 若工作区存在与当前任务无关的未提交改动（如并行任务、临时实验文件），可在调用工具时通过 **`modified_files`** 参数传入本任务实际涉及的文件列表。
- 门禁将只校验这些声明的文件是否干净提交，允许列表外的改动以告警形式通过。

## 硬性卡点

1. **先提交业务代码，再提交工作流簿记**：顺序绝对不能颠倒。
2. **严禁物理删除任务目录**：归档是移动目录持久化保存，严禁使用 `rm -rf` 直接删除历史任务目录，严禁手动搬运文件夹。
3. **严禁执行 `git commit --amend` 篡改历史**。
4. **尊重用户手动提交流**：若用户选择自己手动执行 `git commit`，在用户确认后直接跳到收尾汇报，不要强行重复提出提交计划。
5. **未批准的 spec-delta 禁止合并**：`status` 不是 `approved` 就停下询问；但**文件不存在不算未批准**（见第 0 步第 1 条）。
6. **核对失败禁止静默处理**：旧文本对不上、锚点缺失或重复时停下询问，绝不「差不多」匹配或顺手改原文。
