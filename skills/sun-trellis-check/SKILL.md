# sun-trellis-check

在每个实施阶段块结束时，以及提交代码前作为全量验证阶段运行本技能：对照规范与产物严格检验代码，就地修复发现的问题，确保全部测试绿灯且有效。

## 第一步：定范围（改动集必须确定性算出）

改动集只能由工具算出，**不许由模型凭印象列文件**。在规范上下文之前先跑：

```text
git rev-parse --show-toplevel          # 仓库根
git rev-parse HEAD                     # 本次检查的快照
git diff --name-only <base>...HEAD     # 已提交改动（base = 任务起点提交）
git status --porcelain                 # 未提交改动（新增/删除/重命名/修改）
```

- 取两份的并集去重得到改动集，原样记入产物（feat → `review.md`，issue → `fix-note.md`，refactor → `apply-notes.md`）的「Diff 范围」节。
- `<base>` 取任务创建时的提交；取不到就用 `git merge-base HEAD <主干>`，并在产物里写明实际取值。
- 重命名按「旧路径删除 + 新路径新增」两条记；删除的文件同样要有检查结论（确认没有残留引用）。
- 非 git 仓库或 git 不可用：**停下说明**，不得退化成「凭记忆列文件」再继续。

## 规范上下文与质量门

（第二步取规则的前置：先确认本次有哪些权威文档可查。）

先用 `.trellis/doc.json` 确认本次应检查的文档，而不是只替换路径关键字：

- `root`：Skill 的文档根目录，用于把 `$root/<package>/<layer>/index.md` 展开为实际路径。
- `files`：运行时注入白名单，每项是项目根相对的完整 Markdown 路径；root 不参与它的拼接或过滤。
- 先读 files 中与改动相关的规范；有导航/index 文件时先读导航，再沿链接找质量门。需要按 root 查目录时，先展开 `$root/...` 再读实际文件。
- 无配置时使用默认 root 和原有目录结构；配置无效或文件缺失时报告并停止，不得回退另一份旧规范。

## 第二步：取规则（路径 → 规则查表）

规则按**改动文件路径**解析，查到什么规则就按什么规则查：

- 用 `.trellis/doc.json` 的 files 与 `$root` 导航，按包 / 层 / 目录定位适用规范；路径越深越具体，冲突时以更具体的为准，并在产物里写明取舍。
- 查不到适用规则的路径，在覆盖清单里标「无适用规范」——**不要临时编一条规则**，也不要把别的层的规则套上来。
- 规则文件缺失或配置无效：报告并停止，不得回退另一份旧规范（同「规范上下文与质量门」）。

## 检查矩阵

| 检查维度 | 执行命令 / 检查方式 | 通过标准 | 发现问题处理规则 |
|---|---|---|---|
| 1. 类型检查 | 如 `pnpm run type-check` 或 `tsc --noEmit` | 0 errors | 就地修复类型定义或类型断言问题 |
| 2. 代码风格与规范 | 如 `pnpm run lint` | 0 errors | 能 auto-fix 的直接修复，其余就地手动调整 |
| 3. 测试有效性审查 | 检查测试是否只照抄旧实现内部细节（刻舟求剑） | 测试对准接缝且断言业务不变量 | 若测试只是刻舟求剑，重写为外部接缝契约测试；严禁迁就坏测试打补丁 |
| 4. 单元 / 集成测试 | 如 `pnpm test` 或运行对应测试文件 | 全部通过（绿灯） | 修复实现逻辑；若为需求变更同步更新对应单测 |
| 5. PRD 验收标准 | 对照 `prd.md` 中的 Acceptance Criteria 逐条核对 | 100% 满足 | 若行为不符继续补齐逻辑 |
| 6. 规范门禁 | 按上方“规范上下文”读取 files 与 `$root/...` 展开后的质量门 | 遵循分层依赖与约定 | 修正越界调用或非规范实现；配置模式不要回退未列入 files 的旧文档 |

## 覆盖清单（逐文件结论，漏一个不许收工）

改动集里的**每个文件**都要有一行结论，写入产物的「覆盖清单」节：

| 文件 | 适用规则 | 结论 | 依据（命令/行号/输出片段） |
|------|----------|------|------|
| | | 通过 / 有问题（已修/待修） / 无适用规范 | |

- 清单行数与改动集文件数对不上，即视为未完成——不许只写「已全量检查」了事。
- 结论必须带依据；没有依据的行按「未检查」处理。

## fail-closed（工具失败一律算错误）

- 检查工具失败**一律算错误**：非零退出、无输出、输出被截断、超时、被取消、结果解析不出结论。
- 禁止把「命令没跑起来」「输出看不懂」「环境缺依赖」记成「干净」；报错要带命令、退出码与输出片段。
- 连续失败先修工具或环境，**不许换一条更弱的命令凑绿灯**（例如跳过类型检查只跑 lint）。

## 跨模块一致性与全量终审（Full-scope pass）

- **跨包一致性**：改动涉及多个分层或包时，逐个验证每个受影响包的质量门，防范中间迭代产生的联动问题。受影响包用图查询（`detect_changes --scope impact` / `trace_path`）枚举，**不要靠 grep 猜范围**；图服务不可用时按 `_templates/graph-queries.md` 降级为文本检索，并在产物里写明降级与「未覆盖」部分。
- **全量终审**：在进入 `commit` 阶段前，对所有受影响的包执行一次最终全量检查，杜绝局部验证未能捕获的隐患。

## 产物记录与反馈

- **feat 轨道**：将改动集、覆盖清单、检查命令、执行输出与验证结论记入 `review.md`。
- **issue 轨道**：将改动集、覆盖清单、测试结果与修复验证证据记入 `fix-note.md`。
- **refactor 轨道**：将改动集、覆盖清单与行为等价的回归验证记录记入 `apply-notes.md`。

## 硬性卡点

1. **改动集由工具算出并落盘**：没有 `git diff` / `git status` 证据的「改动范围」不算数。
2. **覆盖清单不许有洞**：改动集里任何文件缺结论，禁止收工。
3. **fail-closed**：工具失败按错误上报，禁止报「干净」或「已通过」。
4. **就地修复原则（Auto-fix）**：发现机械性、类型或规范报错，不要只向用户汇报报错，必须直接修改代码并重新验证，直到全绿。
5. **测试绿灯是必要条件而非充分条件**：除了工具无报错，代码改动必须逐条满足任务 PRD 声明的业务验收标准，且断言的是真实业务不变量。
6. **严重缺陷退回规划**：若检查过程中暴露出 `prd.md` 存在严重的业务定义缺陷，必须退回规划阶段更新产物并重新实现，绝不能掩耳盗铃。
7. **未全绿严禁收工**：任何检查项未通过前，严禁宣称任务完成或执行归档。
