# Analysis

## 根因

### 1. 版本号是播种的**唯一**触发条件，却没有被当作发布契约对待

`ensureProjectSkills` 的判定是「版本不等 → 覆写」，这是刻意的设计（同版本零写开销）。
但它把「技能正文变更」与「版本号变更」绑成了同一件事，而提交习惯没有跟着变：
`d26cb1c` 把技能正文当普通文本改，发布时只抬了 `1.1.0` 一次（`cd977d9`），
后续修补直接追加在 `1.1.0` 之上。

失效机制：

```
项目 marker = "1.1.0"  ==  package.json version "1.1.0"
      ↓
isUpgrade = false
      ↓
alreadyExists && !isUpgrade  →  present.push(id); continue   // 不覆写
```

技能正文是**随包分发的资产**，正文变了就是发布内容变了；版本号是这条链路上唯一的分发信号，
所以「改 skills 必抬版本」应当被测试或脚本钉住，而不是靠人记得。

### 2. 播种入口只有一个（运行时），安装器不参与

`ensureProjectSkills` 的调用方只有 `lib/index.js` 的会话启动路径。`install.mjs` 负责
profile 接线（junction / patch 行 / 依赖项），与项目级技能播种完全正交。于是：

- 想「立刻拿新版」没有任何显式命令；
- 唯一后门是删 marker，而删 marker 这件事只写在会话记忆里，不在任何文档里。

设计上缺的是**同一份实现的两个入口**（运行时自愈 + 安装期显式强制），而不是两套逻辑。

### 3. 大 review 停在「名词」层

小 review 之所以可执行，是因为它有：范围来源（`git diff` 确定性算出）、产物（`review.md`）、
证据三要素、轮次上限、不收敛的出口。大 review 这四条一条都没有，只登记了一个外部工具名。
外部工具**不在包内**是本项目明确的取舍（零依赖），所以「缺失时怎么办」不是可选项，是必需项——
`graph-queries.md` 已经给出了范式（不可用 → 退文本检索 + 写明未覆盖范围），大 review 没照做。

### 4. 记录漂移是流程副产物

v1.1.0 条目里的 329 对那个 tag 是准确的（333 − 4 个安装器测试）；偏差出在**增量没被记录**：
`aeabf38` 修了安装器又加了 4 个测试，却没有版本条目，HEAD 实际 333 而文档停在 329。
`files` 漏 `CHANGELOG.md` 同理：加 `FORK.md` 时按需勾选，没有把「发布记录」当成包的一部分。

### 5. tag 与 main 分叉

`cd977d9` 打 `v1.1.0` 之后又落了一个修复提交（`aeabf38`），版本号没动 ⇒ tag 名（1.1.0）
与其内容（含安装器修复）不一致，`git checkout v1.1.0` 会拿到带 Windows 安装器 bug 的版本。

## 为什么之前没被发现

- 333 项测试全部针对**源码**技能文本与 `ensureProjectSkills` 的单元行为，没有一条断言
  「`package.json` 版本与 `skills/**` 变更同步」——这类跨文件契约没有测试就必然漂移。
- 安装器此前零测试覆盖（`aeabf38` 才补上 4 个），自然也没有 `--reseed` 的行为测试。

## 修复方向（不做过度设计）

1. 抬版本到 `1.1.1`（最小、直接，把已播种项目推入 `isUpgrade` 分支）。
2. `install.mjs` 增加 `--reseed` / `--project`，**复用** `ensureProjectSkills`，
   用一个 ~15 行的 `node:fs` 适配器接上，不复制播种逻辑。
3. `work-types.md` 补「大 review 怎么跑」：入口检查命令、`delegate` 模式的执行口径、
   缺工具时的降级清单与记录要求（不发明工具不存在的 flag）。
4. CHANGELOG 回填真实数字与新增条目；`files` 补 `CHANGELOG.md`。
5. tag 理顺：`v1.1.0` 移到 `aeabf38`（版本号仍是 1.1.0、且含安装器修复），
   新提交打 `v1.1.1`。

## 不做什么

- 不引入「技能正文哈希」之类的额外机制（YAGNI：版本号已足够，问题在没抬版本）。
- 不把 OCR 二进制打进包（既定取舍）。
- 不改既有 333 项测试的语义。
